App\Microblog: flat files keyed by ULID

We mirror App\Blog's layering in App\Microblog and store each message as a Markdown file named {ULID}.md on its own microblog disk — a message has no title and so no natural slug, and its sort order must survive edits, so both identity and posted_at have to be explicit data rather than filesystem facts.
Driver
specifications/features/microblog/**.feature — the composer, the admin list, and the homepage section
Related
Extends ADR 0001 — the precedent for file-based house layering, here applied to a second content domain rather than an operational one.

The rules

  • Disk — a new microblog disk at storage_path('app/private/content/microblog'), added to config/filesystems.php next to posts and meta.
  • Identity is a ULID. Illuminate\Support\Str::ulid() at creation (ships with Laravel, no new dependency), never changing; the file is {id}.md. It is the route parameter for the composer's edit screen and the admin list's edit/delete links, and what “a message that does not exist” (Microblog composer 06) checks against. Being independent of the body, update is a plain overwrite — none of the rename-on-change dance PostWriteRepository needs for slugs.
  • Front matter carries id and posted_at only — no title, excerpt or draft flag. posted_at (Y-m-d H:i:s) is written once at creation, and update must read the existing file's value and carry it forward unchanged, replacing only body. This is the mechanism that makes Microblog composer 05 hold: the sort key can never be filesystem mtime, so it survives edits, copies and deploys.
  • No Markdown-to-HTML conversion — messages are plain text, so the parser/serializer pair is simpler than Blog's: no converter, no excerpt derivation.
  • Sorting mirrors PostSorter: a MessageSorter sorts posted_at descending. No PostFilter equivalent — nothing is ever a draft.

Why

Storage was the user's call: an Eloquent table was recommended — a natural auto-id solves the missing slug and ORDER BY posted_at solves sorting and scale for free — but the user chose flat files, to keep every content domain git-trackable and consistent with App\Blog / App\About. That leaves identity and sort key, and flat files answer neither on their own: without a title there is nothing to derive a filename from, and the one ordering guarantee the spec makes is precisely the one mtime breaks.

Why not

OptionWhy not
Eloquent model + microblog_messages migrationRecommended to the user (auto-id, cheap ORDER BY, no directory scan per request); rejected by them in favour of file-based, git-trackable content
Sequential integer filenames (1.md, 2.md, …)Needs a scan of existing files to compute the next id on every create — race-prone work a locally generated, URL-safe ULID avoids entirely
Filesystem mtime as the sort keyViolates Microblog composer 05 outright: a touch, a redeploy, or the OS's write behaviour during an edit silently reorders messages
Reusing the posts diskMixes two front-matter shapes on one disk and forces all() scans to filter by shape; each domain already gets its own disk

Fallout

  • New App\Microblog namespace and microblog disk. No new dependency, no migration, still no content database table — that question is deferred, not closed; a future domain with a genuinely different access pattern can still make the case in its own ADR.
  • The update path must preserve posted_at by reading it back from the existing file rather than accepting it from the caller. Correctness requirement, not a style preference.
  • Listing messages parses every file on the disk per request, like PostSource::all() does today. Acceptable at the expected volume; the leesmij's revisit-if-volume-grows note applies to both domains together.
  • The 280-character cap and non-empty-body validation are per-feature behavior, left to feature-development.
