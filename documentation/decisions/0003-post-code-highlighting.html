0003 Accepted 2026-07-22

Syntax highlighting: tempest/highlight, scoped to posts only

We add tempest/highlight, wire it into a second post-only converter, and port Catppuccin Latte/Mocha into our own --hl-* CSS variables — the shared PostMarkdownToHtmlConverter also renders the About bio, and the site's light/dark toggle is client-side only, so neither the converter nor the vendor theme files can be used as they are.
Driver
specifications/features/blog/frontend/post_code_highlighting.feature
Related
Corrected in part by ADR 0004 (points 2 and 4). ADR 0005 settles how the theme scenarios are verified. ADR 0009 moves point 2's plain converter to App\Markdown.

The rules

  1. Add tempest/highlight (composer require tempest/highlight) — approved by the user.
  2. PostMarkdownToHtmlConverter stays exactly as it is and keeps serving App\About\AboutFactory; that is what keeps scenario 07 (an unhighlighted bio) true by construction. A new class in App\Blog\Markdown (indicative name HighlightedPostMarkdownToHtmlConverter; exact shape is feature-development's call) builds its own Environment with highlighting, and PostFileParser uses it in place of the current converter. Only post bodies go through it.
  3. No app-level handling for unknown or missing languages. The library's Highlighter already falls back to TextLanguage and never throws, which satisfies scenarios 02–03. The existing catch (CommonMarkException $e) stays as the safety net for genuine conversion errors, unchanged.
  4. Never use the inline {lang} opt-in syntax in editorial content or tooling.
  5. Theme values are ported into our own CSS, never imported. Add --hl-* custom properties to resources/css/app.css, declared in :root with the Latte values and re-declared in .dark with the Mocha ones, mirroring the existing --t-* pattern; then a small hand-written set of .hl-* rules scoped under .prose, each referencing its var(--hl-*). Skip the vendor themes' base pre, code { background-color } rule entirely — .prose pre already forces var(--t-surface) !important, so only token foregrounds are needed. Which tokens beyond the table below get ported is feature-development's call, driven by what php, javascript and bash actually emit.
On points 2 and 4, read ADR 0004 first: registering the whole HighlightExtension also registers an inline-code renderer, so not writing the {lang} prefix is necessary but not sufficient.

Why

tempest/highlight plugs into the League\CommonMark\Environment\Environment that post bodies already go through, so highlighting happens server-side in the existing pipeline with no new JS. Two things then have to be worked around.

The converter is shared with About, so highlighting must be scoped by using a different converter rather than by changing the shared one. And the theme toggle is a .dark class flipped in the browser, while the library's ~48 bundled theme files target unscoped global selectors with hardcoded hex values (catppuccin-latte.css: pre, code { color: #4c4f69 }, .hl-keyword { color: #8839ef }) — two of them on one page fight over the same selectors with no scoping mechanism. Porting the values into the --t-*-style variable pattern the project already uses resolves both.

The user approved the dependency and chose Catppuccin Latte/Mocha as the pair.

Fallout

  • New composer dependency and one new class in App\Blog\Markdown. No change to App\About\AboutFactory or its tests.
  • resources/css/app.css gains --hl-* properties and a .prose .hl-* block — no new build tooling, this rides the existing Tailwind/Vite pipeline.
  • Language support is whatever the library ships (php, javascript and bash are confirmed and are what scenario 01 covers). A fourth language later needs no ADR change, only a check of the library's src/Languages.
  • A future need for a different theme (e.g. a per-post override) reopens the one-fixed-pair decision and supersedes this ADR rather than bolting on a case.
