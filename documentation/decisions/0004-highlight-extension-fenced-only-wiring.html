0004 Accepted 2026-07-22

Highlight fenced code only, not the whole HighlightExtension

We register CodeBlockRenderer for FencedCode ourselves instead of adding HighlightExtension — the extension also registers an inline-code renderer, and scenario 04 requires inline spans to never highlight.
Driver
specifications/features/blog/frontend/post_code_highlighting.feature (scenario 04)
Related
Refines ADR 0003, whose dependency, scoping and theme decisions stand unchanged.

The rule

In the post-specific converter of ADR 0003 — and never addExtension(new HighlightExtension()):

php
$environment->addRenderer(
    FencedCode::class,
    new \Tempest\Highlight\CommonMark\CodeBlockRenderer(),
    10,
);

Code::class is never re-registered, so CommonMark's own default inline renderer stays in effect and inline spans render as plain <code> exactly as they do today, prefix or no prefix. Whether this lives inline in the converter's constructor or in a small custom ExtensionInterface implementation is feature-development's call, per ADR 0003's existing latitude on that class.

Why

Tempest\Highlight\CommonMark\HighlightExtension::register() registers two renderers, FencedCode and inline Code, both at priority 10. Its InlineCodeBlockRenderer highlights any span carrying the {lang} prefix, and scenario 04 deliberately puts one in a post body precisely to prove the prefix is inert. So ADR 0003's point 4 — that never writing the prefix is enough — does not hold: adding the extension wholesale fails the scenario regardless of editorial policy.

CodeBlockRenderer is final readonly, public, and is the exact class the extension itself instantiates for FencedCode, so registering it directly reuses the library's real fenced-code rendering without its bundled inline registration.

Why not

OptionWhy not
Add the extension, then re-register Code::class back to CommonMark's default at a higher priorityRequires knowing CommonMark's internal default inline-renderer class and the priority the extension used — coupling to two libraries' internals, for no gain over registering only the renderer we want
Post-process the rendered HTML, stripping hl-* classes from spans inside inline <code>A second pass undoing output that should never have been produced; more code and another place the “never highlight inline” invariant can silently break

Fallout

  • A concrete implementation constraint, not a suggestion: scenario 04's test fails if anyone reaches for addExtension.
  • If a future feature genuinely wants inline highlighting (reintroducing the {lang} prefix as a real editorial feature), that reopens this ADR and should supersede it rather than special-case around it.
