0006 Accepted 2026-07-23

Keeping --min=100 green against an equivalent mutant

We annotate the renderer-priority line with a mutator-scoped @pest-mutate-ignore — the literal 10 produces two integer-magnitude mutants that are provably equivalent, so no honest test can kill them.
Driver
specifications/features/blog/frontend/post_code_highlighting.feature
Related
Annotates the exact wiring line ADR 0004 mandates; 0004's decision is unchanged.

The rule

In FencedCodeHighlightExtension::register():

php
$environment->addRenderer(FencedCode::class, new CodeBlockRenderer($this->highlighter), 10); // @pest-mutate-ignore: IncrementInteger,DecrementInteger

Scoped to exactly those two mutators on that one line. RemoveMethodCall and every other mutator stay active — and RemoveMethodCall is killed, by the extension's covers()-scoped unit test. This is a single documented carve-out authorised by the user (2026-07-23), not a relaxation of the 100% gate.

Why

The survivors are IncrementInteger (10 → 11) and DecrementInteger (10 → 9), and both are equivalent mutants: they change the code without being able to change observable behavior, so there is no test to write. @pest-mutate-ignore is Pest's first-class mechanism for exactly this, used the same way in Pest's own codebase (vendor/pestphp/pest-plugin-mutate/src/Support/MutationGenerator.php:68); the mutator names match the survivors' classes in vendor/pestphp/pest-plugin-mutate/src/Mutators/Number/.

Why the two mutants are provably equivalent
  • CommonMarkCoreExtension registers its own FencedCodeRenderer for FencedCode::class at priority 0 (vendor/league/commonmark/src/Extension/CommonMark/CommonMarkCoreExtension.php).
  • League\CommonMark\Util\PrioritizedList::getIterator() sorts highest-priority-first (krsort) and, at equal priority, preserves insertion order. Core is added first, so at a tie the core renderer wins.
  • This renderer therefore needs priority ≥ 1 to override core — and every value ≥ 1 (9, 10, 11, …) yields byte-identical HTML.
  • No integer literal can satisfy the gate: the only meaningful boundary is ≥ 1 versus ≤ 0, so a +1 and a −1 mutation can never both cross it. Priority 1 makes 1 → 0 killable but leaves 1 → 2 surviving. The magnitude is simply unobservable.

Why not

OptionWhy not
A reflection-based test asserting the renderer is registered at priority == 10Reaches into league's private internals to pin a constant with no behavioral meaning — testing an implementation detail purely to move the score, and making the 100% look earned while hiding that the value is arbitrary
A contrived competing-renderer test registering a second FencedCode renderer at neighbouring prioritiesBehavioral, but leans on league's tie-break ordering and reads as noise; not this codebase's small-explicit-class style
Lower the global --min below 100Throws away the gate's value everywhere to accommodate one line

Fallout

  • feature-development keeps ADR 0004's priority literal 10 and adds the trailing comment; nothing else changes. composer qa's mutation step then reports 100% with zero survivors.
  • The gate stays intact for all other code — this is mutator-scoped and line-scoped, not a policy change.
  • If ADR 0004 is ever superseded and the wiring line changes (an override mechanism without an integer literal, say), this annotation goes with it — it exists only to cover that literal.
