0005 Accepted 2026-07-22

Verify the light/dark highlight scenarios in a real browser

We add pestphp/pest-plugin-browser and assert computed token colours in a headless browser — the theme toggle is entirely client-side, so a GET /blog/{slug} response is byte-identical in both modes and no HTTP test can observe the difference the scenarios describe.
Driver
features/blog/frontend/post_code_highlighting.feature (scenarios 05–06)
Related
Settles what ADR 0003 left open: 0003 decided what the two themes are, this decides how a test observes that they render differently.

The rule

shell
composer require pestphp/pest-plugin-browser --dev
npm install playwright@latest
npx playwright install

Add tests/Browser/Screenshots to .gitignore, per Pest's own setup instructions, since screenshot() may be used to debug failures.

Scenarios 05 and 06 are then verified as browser tests: visit the post's page normally (light — no .dark class without an explicit preference) and again with visit(...)->inDarkMode(), which emulates prefers-color-scheme: dark and so resolves to .dark through the toggle script's 'auto' default, no clicking needed. Read the computed colour of a highlighted token (e.g. a .hl-keyword span inside the rendered <pre>) via script() in both renders; assert the two differ (06) and that each matches ADR 0003's Latte/Mocha value for that mode (05).

This is feature-to-pest's test to write. No production code changes follow from this ADR beyond what ADR 0003 and ADR 0004 already require.

Why

The toggle in resources/views/components/layouts/app.blade.php reads a localStorage preference and flips a .dark class on <html> from an inline script; :root versus .dark custom property values are resolved by the browser at paint time, not by Laravel. The existing HTTP feature tests in tests/Feature/blog/frontend/ structurally cannot express “switched the site theme” or observe a rendered colour — there is nothing different in the response to assert on. Pest v4's browser mode can, and the user chose that over the cheaper proxy below.

Why not

OptionWhy not
Assert resources/css/app.css's :root/.dark blocks contain ADR 0003's hex valuesNeeds no dependency, but verifies CSS source text rather than anything that renders — it passes even if no selector ever references --hl-*, which is exactly the gap a scenario about visible rendering exists to catch. Rejected by the user
A testability-only server-side theme switch (cookie or query parameter forcing .dark)Production surface that exists solely to make tests easier, contradicting the client-side-only design ADR 0003 records as a given

Fallout

  • New dev-only dependencies (pestphp/pest-plugin-browser, playwright) plus a one-time browser-binary download. Dev and CI environments must be able to run that install step — a real cost beyond a composer-only dependency, worth revisiting if CI runtime or image size becomes a concern.
  • The first browser test in this project. It establishes the pattern (inDarkMode() for theme emulation, script() for computed-style assertions) for scenarios that are genuinely client-render-dependent; most scenarios should still be plain HTTP feature tests.
  • .gitignore gains tests/Browser/Screenshots.
